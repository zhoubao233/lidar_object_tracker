### 构建与旁路启动

```bash
cd ~/APS/lidar_object_tracker
bash tools/test.sh

source /opt/ros/noetic/setup.bash
cd ~/APS/EGO-Planner-v2/swarm-playground/main_ws
catkin_make -j2 -l2 tracker_prediction_node traj_utils_generate_messages_py

# 已启动 Gazebo、SITL、MAVROS，且没有另一个 tracker 实例时：

```

已有 RViz 时可以设 `rviz:=false`，自行添加 `/tracker_prediction/markers` 的 MarkerArray。输入基准为 map。
此脚本同时启动 tracker 和预测桥，不需要另开 `run.sh`。M2 新规划入口及输入选择见 [接入说明](EGO_EXTERNAL_OBSTACLES.md)。Ctrl+C 停止该旁路。现阶段继续保留 `lidar2word.sh`，**不能把 EGO 地图切到只含 background 的输入**。

默认参数是调试初值：预测窗 2 s、报告最大年龄 0.5 s、真实观测最大年龄 0.5 s、位置余量 0.2 m、速度误差增长 0.3 m/s；尚未用真机预测误差标定。
当前 clearance 为半对角线加位置余量及全预测窗误差，规划端必须使用一致的几何规则。`valid_until` 仅限制预测轨迹时间范围，消费者还必须检查报告新鲜度；不能凭该字段继续使用已经停更的输入。

## 1. 实施范围与顺序

首版采用单机 GUIDED、单目标点、匀速预测。Gazebo、ArduPilot SITL、MAVROS 和现有控制桥继续复用；先在仿真中完成接入，再验证真机输入和执行。FullGuided 航点业务最后接入，AUTO/GUIDED 自动切换、KF/IMM 和多机功能不作为首版依赖。

顺序：**输入基准核验 → 旁路预测 → EGO 动态输入 → 地图分流 → 切换启动链路 → 飞控闭环验证**。

在动态目标尚未进入 EGO、失效处理未完成之前，不把规划器地图切换成只排除 MOVING 的 background。避免移除了地图中的物体，却没有对应动态避碰约束。

## 2. 工程边界

| 工程 | 拟承担的改动 |
|---|---|
| lidar_object_tracker | 保留独立感知包；贯通坐标参数，补充完整世界点云输出和集成需要的状态信息，完善仿真/真机配置 |
| EGO-Planner-v2/main_ws 新包 tracker_ego_bridge | 读取跟踪报告与点云、预测目标运动、映射目标 ID、构造 EGO 轨迹和环境输入、发布诊断 |
| EGO plan_manage / traj_utils / traj_opt | 增加外部障碍生命周期接口与缓存，复用现有动态代价；统一优化和安全检查的预测有效期处理 |
| EGO plan_env | 接入分流后的环境点云，补齐局部占据更新、旧占据清理及纯点云输入状态 |
| EGO launch / tools / RViz | 提供 tracker 输入模式、统一参数和可视化，保留旧输入方式用于对照 |
| uav_application | 单点闭环通过后接入 FullGuided 任务与控制权流程 |

tracker 不直接依赖 EGO 的 traj_utils；桥接包承担两个工程之间的适配。以上包名和新增接口名为拟定名称。

## 3. M0：固定输入基准和对照数据

**要做的事**

- 核实当前 mission_auto_avoid 场景实际发布的 Livox 消息、点时间、帧名称、雷达安装位置，以及 MAVROS 位姿对应的机体基准。
- 当前场景配置中雷达安装高度为 0.38 + 0.05 = 0.43 m；它不同于 tracker 旧仿真默认 0.235077 m。将外参写入该场景专用配置，不覆盖其他场景或真机外参。
- 仿真适配器仅接受瞬时扫描。确认 offset_time 是否全零；若存在真实逐点扫描时间，使用经过时间核验的去畸变输入路径，不能直接按瞬时帧处理。
- 统一以 MAVROS 的本地 map 为首版内部坐标基准。规划、目标、地图、模型和 RViz 同步配置；需要 world 兼容时仅在确认同一原点/方向后配置静态变换，禁止只改 frame_id 冒充变换。
- 录制一段原始雷达、里程计、飞控状态和旧链路输出，包含静态环境及一个运动目标，作为后续对照输入。
- 在隔离环境或旁路命名空间运行 tracker，核验静态环境不会因飞机运动被大量判断为动态。

**验收**：完整配对持续输出；坐标对齐；时间年龄可追踪；记录实际帧率、处理延迟和地面有效状态。外参/时钟有问题时先定位，不靠放宽运动阈值掩盖。

## 4. M1：实现预测桥，先旁路显示

**要做的事**

- 新建 tracker_ego_bridge，先读取现有 tracks JSON，不要求先改造整个 tracker 消息体系。
- 根据位置 p0、世界速度 v 和状态时间 t0 生成匀速预测：p(t) = p0 + v × (t - t0)。明确输入中心对应的时刻，避免对 tracker 已外推的 PREDICTED 中心重复补偿。
- 将轨迹编码为现有五次 MINCO 表达；匀速段使用一致的起终点位置、速度、零加速度，避免人为拟合出弯曲或加速。
- 使用目标尺寸与可配置误差余量构造保守范围。现有接口只有标量 clearance，首版采用能包住目标的几何近似；预测误差余量在有限预测窗内取保守值。
- 映射到有界的 EGO 障碍 ID 空间，与无人机 ID 分离。地图分流和目标缓存以同一组 ID/状态为依据。
- 区分 MOVING、STATIC、UNKNOWN、PREDICTED，记录上次真实观测时刻；短时丢失仅在有效期内预测，reset 时清理旧状态。
- 拒绝非有限值、错误坐标、倒序/过旧报告及非法尺寸；没有目标的新鲜帧与感知停更必须区分。
- 发布预测轨迹 Marker、包围范围、输入年龄和目标计数，暂不接入执行中的 EGO 输入。

**验收**：用合成运动验证位置和时间计算，用录包验证 ID 连贯性、停止/遮挡/reset；RViz 可同时观察实测目标与未来轨迹。预测误差按预测时距统计。

## 5. M2：接入 EGO 动态避碰和生命周期

**要做的事**

- 保留 MINCOTraj 作为轨迹内容，但新增独立外部障碍输入，避免与原有多机广播的启动顺序和 ID 语义混用。
- 拟增加外部障碍数组消息，携带坐标、报告时间、会话/reset 标识、输入健康状态，以及每个目标的 MINCO 轨迹、真实观测时间和有效截止时间。
- 数组按完整快照解释：新鲜空数组表示当前无目标；停更不解释成环境清空；新快照中移除的目标按明确策略失效。
- EGO 接收后维护独立外部目标缓存，在现有动态距离代价中复用这些轨迹。
- 优化器与安全检查共用同一目标状态查询、几何余量和有效期规则。有效期外不无限外推，也不能让两个模块各自解释。
- 目标失效、感知停更或 reset 时先进入约定的保持/重规划流程，避免缓存悄悄消失后继续沿旧轨迹执行。
- 此阶段在隔离单机规划测试中验证，地图仍保持保守环境表示。

**验收**：相同地图和目标点下，加入横穿目标后能观察到动态代价和轨迹变化；空快照、停更、删除、乱序、重启均有明确结果；原有多机输入行为不被破坏。

## 6. M3：环境点云分流与地图更新

**要做的事**

- tracker 补充未经动静筛除的完整世界点云输出，作为对照、可见性判断和必要的保守回退输入。
- 将完整点云、background、uncertain 与 tracks 按同帧时间关联；超时或缺项不输出不完整的“已安全分流”结果。
- 已确认且有有效预测覆盖的动态目标，不长期写入静态地图。无法形成有效预测的对象保留保守局部占据。
- UNKNOWN 保留局部障碍表达。注意 uncertain 已包含在 background 中，避免重复融合。
- 增加局部临时占据的更新/到期规则；静态环境维持可见性支持的清除或衰减。处理物体从静止变运动、从运动变静止时的地图交接。
- 旧占据清理不能简单清空整个目标包围框，避免误删重叠墙体；也不能每帧无条件清空所有未看到的静态环境。
- 纯点云输入增加新鲜度状态，传递给系统联动，不依赖深度图超时标志。
- 对感知状态不健康的帧，不继续沿用“动态点已安全交给预测”的假设。

**验收**：静止→移动→停止场景中，旧位置不会长期残留，实际障碍不会在地图与预测之间同时丢失；目标靠墙或遮挡时不会误清静态结构。预测失效与地图回退联合验证。

## 7. M4：统一启动并替换旧点云链路

**要做的事**

- 增加专用单机 tracker 集成 launch 和配置，显式加载 tracker_ws、EGO main_ws 以及驱动消息依赖。
- 为 tracker 的仿真和真机 launch 贯通 world_frame、body_frame、外参等参数；真机外参单独必填，不继承 Gazebo 数值。
- 在 EGO 单机入口选择 legacy 或 tracker 输入。tracker 模式接入新地图和动态预测，禁止同一个输入 topic 存在新旧双发布者。
- RViz 提供环境点云、动态簇、目标预测、飞机模型、规划轨迹与诊断显示。集成模式只启动一个 RViz，避免同名节点互相替换。
- 外部世界 TF、坐标配置和点云转换职责全部迁移后，tracker 模式不再启动 lidar2word.sh。
- 编写启动/停止、录包、回退与故障检查说明。停止控制桥仅意味着停止输出，任务退出还必须明确飞控侧的控制权和模式处理。

**拟定最终启动顺序**

1. Gazebo mission_auto_avoid。
2. ArduPilot SITL。
3. MAVROS。
4. 新集成入口：tracker + 预测/地图桥 + 单机 EGO + 控制桥 + 可选 RViz。
5. 完成单点验证后，再启动 uav_application 的 FullGuided 业务。

旧 lidar2word.sh 在前期旁路验证阶段继续保留。只有 M0～M3 通过并完成 M4 切换，才从新的启动流程移除。以上是目标结构；当前只有 start_tracker_shadow.sh 旁路入口，完整规划集成入口尚未实现。

**验收**：冷启动一次可连通；没有手柄障碍生成器、假里程计或旧转换器依赖；地图和目标预测同时进入同一 EGO；回退旧模式后仍可运行。

## 8. M5：飞控反馈闭环与真机验证

**分层验证**

1. 合成输入和录包：验证预测、分流、有效期与重置行为。
2. Gazebo + ArduPilot SITL：单点任务，依次覆盖静态环境、横穿、迎面、停止/反向、遮挡和输入中断。
3. 业务层：FullGuided 航点及到达、退出行为；不把尚未完成的 AutoAvoid 模式混入验收。
4. 真机地面采集：检查实际雷达时间、外参、定位、动态跟踪与预测误差。
5. 受控真机飞行：依据前面数据确定速度、距离余量和退出条件，再验证实际运动目标场景。

**记录指标**：实际最小间距、真实位置到目标误差、预测误差随时距变化、轨迹跟踪误差、输入到执行延迟、规划耗时与失败次数、输入失效后的行为。阈值按实际机型和测量结果制定，不直接照搬 demo 的 clearance 或当前 3 m/s 启动参数。

真机飞行验证需要现场实施，本计划和软件测试不替代该项。M0～M5 全部满足后，才把流程状态更新为已完成真机闭环验证。
